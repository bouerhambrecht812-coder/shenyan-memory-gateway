01

问题

大模型没有记忆。每次开新对话，它都是一张白纸。对普通问答没什么，对角色类产品是致命的——用户聊了一百轮，它还是会问“你刚才说什么”，而“记得住”恰恰是这类产品付费的理由。

现成的两条路都不太合适。把全部历史塞进上下文：贵、会漂移、聊得越久越乱。交给第三方记忆服务：等于把最私密的对话和角色设定一起交出去，而且写进记忆的内容你事后查不到、改不动。

PAIN 01

上下文断点

超出窗口就忘。用户提到的事，只有正在窗口里那部分才算“发生过”。

PAIN 02

人设漂移

角色自己编的日常（咖啡、拼图、某位亲戚）会悄悄变成“事实”，跑得越久越偏，产品方无法纠错。

PAIN 03

数据失控

记忆存在别人的云上，删除、迁移、审计都要等对方排期。用户最私密的那部分不在自己手里。

谁需要它

场景记忆要解决的不解决的后果
AI 陪伴 / 角色对话跨会话记得用户的偏好、称呼、说过的承诺用户觉得“它根本不在意我”，次留断崖
虚拟人 / 数字员工对外口径一致，品牌设定不被模型即兴改写公开发言出现不该出现的设定
游戏 NPC长线剧情里记得玩家做过什么选择剧情线割裂，重玩价值下降
多角色 IP 运营一个角色一套库，角色之间不串味角色人设互相污染
02

产品

一个可以塞进任何对话产品里的记忆层。它不生产角色，也不训练模型；它负责三件事：把该记的记住、记住的东西可检索、检索出来之前先问过你。

CAPABILITY 01

跨会话记忆

每轮按当前输入检索，最多注入 12 条已确认记忆 + 近 10 轮对话。换设备、重开会话，角色还认得人。

CAPABILITY 02

写入有人审

模型每 5 轮提取最多 3 条候选，必须带原文证据（basis_quote）且能在用户发言里逐字命中，才能进待审队列。

CAPABILITY 03

数据自持

一个 SQLite 文件，212 KB 装下 118 轮对话。备份是复制文件，迁移是拷走文件，删除是删掉文件。

CAPABILITY 04

零改造接入

实现 /v1/chat/completions 与 /v1/models。客户侧只改一个 Base URL 和模型名，业务代码一行不动。

CAPABILITY 05

知道外面发生了什么

通过 MCP 接入时间、天气、头条，每轮按需注入「当前情境」。情境带 TTL，过期即失效，而且不写进记忆库。

CAPABILITY 06

文字之外

回复可以带表情和语音。模型不画图，只在素材库里选，所以不会凭空造出图片地址；动作以列表返回，通道各自渲染。

接入方式是三个字段

# 任何 OpenAI 兼容客户端 / Agent 框架 / IM 适配器
Base URL   http://shenyan-memory:8000/v1
API Key    <网关密钥>
Model      shenyan

做到这一层的好处不是“支持 OpenAI”，而是渠道可插拔：IM、网页、App、客服系统，谁调这个接口谁就能拿到同一套记忆，换渠道不用动记忆层。

03

架构

记忆层在中间，两头都不绑定：左边是渠道，右边是模型。今天接 QQ，明天接网页，记忆层不用改。

网关旁边还挂着两样东西，都不参与记忆写入：一路 MCP 世界事件（时间 / 天气 / 头条，走 stdio 的 JSON-RPC），一个表情素材库（模型只选不画）。

阿里云上怎么落地的

部署写成了一支可以重复执行的脚本，不是一堆手敲的命令。它按这个顺序把一台空机器变成能跑的服务：

阶段做了什么为什么这么做
系统兜底内存不足 2 GB 且无 swap 时，自动加 2 GB swap 并设 vm.swappiness=102 GB 实例跑三个容器，没有 swap 会在登录环节 OOM
密钥生成首次运行用 openssl rand 生成各组件密码，写进 .env 并 chmod 600不让人手填密钥，也不让改过的配置在重跑时被覆盖
握手预置直接写好两端的反向 WS 配置，token 对齐省掉后台里点二十个下拉框，也避免两边配置漂移
镜像回退拉取顺序：官方 → DaoCloud → 镜像站，失败自动改写镜像地址国内到 Docker Hub 经常超时，这是一路踩出来的
开机自启写 systemd unit（oneshot + compose up -d），最后 ss -lntp 自检端口没漏出去重启机器不该需要人登录进去敲命令
04

记忆模型

这是整个产品里唯一真正有门槛的部分：记忆不是自动写进去的，而是走一条四步的审核回路。

01 · 对话网关记下每轮问答，检索相关记忆拼进系统提示
02 · 提取每 5 轮触发一次，JSON 模式提取最多 3 条候选
03 · 待审候选带原文证据进队列，正史不动
04 · 裁决用户确认 → 正史；拒绝 → 标记，不再出现

三道闸门

闸门规则
证据必须逐字命中basis_quote 必须出现在本段对话里，且至少有一处来自用户的发言。角色自己编的日常不算数。
敏感信息不提取健康、财务账户、身份资料一律跳过；模型返回 sensitive 非 false 的直接丢弃。
重复内容不堆叠与已有记忆字符重合度超过 0.82 的候选直接跳过，避免同一件事记二十遍。

两级时间线

不是所有「发生过的事」都该被记住。天气、头条这类信息只在当轮有用——写进正史的话，角色三个月后还会记得那场雨。所以世界事件先落进情境层，过期就没了。

层内容寿命进正史吗
情境层现在几点、外面下不下雨、最近的头条十分钟，超时重取不进
正史层关系变化、角色的人生事件、明确纠错永久要人审

一轮真实的审核

下面的对话是合成示例，用来演示流程；不含任何真实用户内容。

用户
上个项目代号是什么来着？
沈砚
Atlas
沈砚
你三月提过一次，我记着
用户
记忆待审
沈砚
待审核记忆： 
#31 [user_preference] 对方所在团队的项目代号为 Atlas
用户
确认记忆 31
沈砚
记忆 #31 已确认并进入长期记忆。

指令走的是普通消息，不是斜杠命令——这样在任何 IM 里都能用，也不会被适配器截获。上一条候选在确认之前，对后续对话完全没有影响。

为什么不用向量库

20 多条记忆，字符二元组 + 类型加权（纠错 3.0、关系锚点 2.3、核心设定 1.5）就已经足够准。上 embedding 只会多一个几百兆的依赖和一个新的失败点。等记忆过了两三百条再换——这是有意做的延迟决策，不是没做。

为什么坚持人审，而不是自动记忆

角色能不能记住，不是模型能力问题，是谁有权决定“什么算发生过”。

把这条权力交回给使用者，代价是每五轮要回一次指令；换来的是角色不会越跑越偏，也不会把一句玩笑记成事实。每条记忆都带 source 与 basis_quote，任何时候都能追回原话。

06

商业化

这一节是产品化的推演，不是已发生的事实——目前是一套自用的私有化部署，没有对外销售。

三种交付形态

MODEL 01

私有化授权

按实例授权，部署在客户自己的服务器上。适合对数据出境敏感、或有内网要求的中大型客户。

MODEL 02

多租户 SaaS

一个角色一个库，按角色数或月活计费。需要先补上多租户隔离、审计日志与计费埋点。

MODEL 03

SDK / 中间件

嵌进客户已有的 Agent 框架，只提供记忆读写与审核 API，不碰对话链。

和现成方案的位置关系

按公开资料整理的定性判断，未做逐项实测对比。

方案强在弱在适合谁
云端记忆层（Mem0、Zep 一类）开箱即用、工程成熟、规模化数据托管在第三方，写入内容不可审计，定制受限于它的抽象快速验证、无数据合规压力的团队
直接把历史塞进上下文零成本、零集成越聊越贵，长会话必然漂移短会话、一次性问答
沈砚记忆网关数据自持、写入可审、渠道与模型都不绑定单实例、检索朴素、缺多租户与埋点中文角色类产品、有私有化要求

接下来做什么

  • V1.0 · 已交付单角色私有化部署，四层链路，离线测试与运行日志可复现。
  • V1.1 · 已交付MCP 世界事件（时间 / 天气 / 头条）、带 TTL 的情境层、动作协议（文字 / 表情 / 语音）、素材库与标记解析。
  • V1.2 · 多租户会话隔离已经在网页版验证过；下一步把它做成一等公民，补审计日志与计费埋点。
  • V1.3 · 检索升级向量后端做成可插拔，先留着字符匹配做兜底，A/B 出切换阈值。
  • V1.4 · 管理台记忆列表、来源追溯、批量纠正，以及素材库的可视化编辑。
  • V1.5 · SDK把审核回路和动作协议抽成独立包，让客户用自己的对话链也能接。
07

边界与没做好的地方

合规与风险

  • 面向公众提供服务需要备案。按《生成式人工智能服务管理暂行办法》，公众可用的生成式服务要做算法备案与安全评估。当前是私有部署、单人使用，不对外提供服务；一旦 SaaS 化，这是必须先解决的前置条件。
  • 非官方协议接入有平台风险。依赖协议客户端的渠道（如 QQ）可能被平台风控，账号会被限制。这正是把记忆层与渠道层拆开的原因：换渠道不动数据，也不动审核逻辑。
  • 记忆里会有个人信息。当前 SQLite 未做磁盘级加密，删除也不做物理擦除。生产环境需要补字段级加密、留存期限与导出删除通道。
  • 角色是虚构的。案例中的角色由作者与 AI 共同构建，所有设定与对话均为虚构示例。

没做好的地方

  • 没有埋点。access log 只有状态码，没有 request id 和耗时。这是下一步最该补的五行代码。
  • 流式是假的。stream=true 返回 SSE 格式，但内容是整段生成完再一次性发出，不是逐 token。
  • 检索会撞墙。字符二元组在 20 多条记忆上够用，到两三百条就会出现“关键词对得上、语义不对”的召回。
  • 测试只覆盖离线路径。模型超时、429、余额不足这些分支一个用例都没有，靠运行时 except 兜底。
  • 健康检查只看端口。/healthz 通了不代表能回话——真正的端到端探针需要一条不花钱的固定问答。
  • 不支持图片理解。用户发的图在网关层被丢弃，角色看不见。表情和语音是输出侧的能力，输入侧仍然只有文本。
  • 语音只有协议没有 TTS。网页端用浏览器自带的语音合成顶上，QQ 端要发真实语音还得接一个 TTS 服务。
  • 没有多租户。网关假设一个实例服务一个角色。网页演示版靠独立数据库文件绕过去了，那是权宜之计，不是架构。
